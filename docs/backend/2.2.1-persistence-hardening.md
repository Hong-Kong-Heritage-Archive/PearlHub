# Chat 2.2.1 — PostgreSQL Persistence Hardening

## Objective

Harden the existing PearlHub PostgreSQL persistence implementation against invalid database states.

The current skeleton already implements:

```text
Domain → Application → Repository Interfaces → PostgreSQL Adapter → PostgreSQL
```

Keep that architecture unchanged.

## 1. Artifact identity immutability

`owner_id`, `name`, and `slug` are immutable after creation.

Add PostgreSQL-level protection. `visibility`, `status`, and `updated_at` must remain updateable for normal lifecycle operations.

Integration tests must prove direct SQL UPDATE attempts for all three identity fields fail and leave the original Artifact unchanged.

## 2. Tombstone invariant

The frozen deletion model is:

```text
active → tombstone + unlisted
```

Reject:

```text
status = 'tombstone' AND visibility <> 'unlisted'
```

Prefer a PostgreSQL CHECK constraint.

Test:
- active/public valid
- active/private valid
- active/unlisted valid
- tombstone/unlisted valid
- tombstone/public rejected
- tombstone/private rejected
- DeleteArtifactService still produces tombstone + unlisted

## 3. Dependency resolution integrity

A dependency has:

```text
target_artifact_id
```

A resolution has:

```text
resolved_artifact_version_id
```

The resolved version must belong to the dependency target Artifact.

Reject a resolution where the resolved version belongs to another Artifact.

Preserve the existing public domain API. Use the smallest schema/constraint change necessary, inspecting current keys/FKs first.

Test:
1. dependency targeting Artifact A + A version → succeeds
2. dependency targeting A + B version → fails

## 4. Preserve existing Version immutability

Do not weaken existing database protection for Artifact Versions.

The persisted Version remains immutable, including:

- artifact_id
- version
- content_hash
- content_location
- created_at
- published_at

Test direct SQL UPDATE and DELETE rejection.

## 5. Verify existing uniqueness

PostgreSQL must continue enforcing:

```text
UNIQUE(owner_id, slug)
UNIQUE(artifact_id, version)
UNIQUE(artifact_id, content_hash)
```

Test:
- same-owner duplicate slug rejected
- same slug for different owners accepted
- duplicate version within Artifact rejected
- same version across different Artifacts accepted
- duplicate content hash within Artifact rejected

## 6. Foreign-key integration tests

Using real PostgreSQL, verify:

- Artifact invalid owner → reject
- Version invalid Artifact → reject
- Lineage invalid parent/child → reject
- self-lineage → reject
- Provenance invalid version → reject
- Dependency invalid source version → reject
- Dependency invalid target Artifact → reject
- Resolution invalid dependency → reject
- Resolution invalid version → reject
- Compatibility invalid source version → reject
- Compatibility invalid target version → reject

Do not replace FK enforcement with application existence checks.

## 7. Lineage

Preserve:

```text
relationship_type = fork
parent_artifact_id <> child_artifact_id
UNIQUE(parent_artifact_id, child_artifact_id, relationship_type)
```

Test valid fork, duplicate fork, self-lineage, Clone creates no lineage, and normal Artifact deletion does not physically delete lineage.

Do not add Merge or Branch.

## 8. Physical Artifact deletion

Keep the existing no-physical-delete policy.

Direct:

```sql
DELETE FROM artifacts WHERE id = ...
```

must fail.

Application deletion must still be a tombstone update.

## 9. Transactions

Use the existing framework-independent `TransactionManager`.

Add a real PostgreSQL integration test proving rollback, for example:

```text
BEGIN
  create Artifact
  create Version
  create Dependency
  force failure
ROLLBACK
```

After failure, none of the newly created records remain.

Do not use a fake transaction implementation for the PostgreSQL integration test.

## 10. Concurrent uniqueness

Where practical, test concurrent attempts to create the same `(owner_id, slug)`.

Exactly one should succeed; the other should fail on the PostgreSQL unique constraint.

Do not replace the database constraint with SELECT-then-INSERT logic.

If the environment makes the concurrency test unstable, document the limitation.

## 11. Migration

Add a new forward-only migration, e.g.:

```text
migrations/002_persistence_hardening.sql
```

Do not modify `001_initial.sql`.

Only add constraints/triggers/supporting keys needed for this hardening.

Do not add unrelated tables or provider-specific storage tables.

## 12. Repository boundaries

Do not change repository interfaces unless an existing defect requires it.

Do not expose `Pool`, `PoolClient`, PostgreSQL transaction objects, SQL, or PostgreSQL error classes through domain/application interfaces.

Translate PostgreSQL constraint errors at the persistence/application boundary using the existing error model.

## 13. Explicitly out of scope

Do not introduce:

- Prisma
- Drizzle
- Kysely
- TypeORM
- Hono
- Fastify
- NestJS
- Express
- S3/MinIO/GCS
- durable content storage
- HTTP API
- authentication
- frontend
- Playground
- semantic search

## 14. Acceptance criteria

Do not claim completion until:

1. `npm run build` passes.
2. Existing unit/application tests pass.
3. PostgreSQL integration tests pass against real PostgreSQL.
4. A new forward-only hardening migration exists.
5. Artifact owner/name/slug are DB-protected.
6. Tombstone implies unlisted.
7. Dependency resolutions cannot point to the wrong target Artifact.
8. Artifact Version immutability remains enforced.
9. Existing uniqueness/FKs remain enforced.
10. Physical Artifact deletion remains rejected.
11. Real transaction rollback is tested.
12. No HTTP framework or ORM is introduced.
13. Chat 2.1 frozen decisions remain unchanged.
